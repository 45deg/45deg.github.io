Practical refinement contracts

These examples describe reusable operations without tying them to a particular application. An ordinary type describes the shape of a value. A refinement adds what must be true about that value, often in relation to another argument.

The playground retains Keep a value within bounds as its single basic example. Allocation and window reading remain standalone exercises under examples/practical/; paste their source into the editor and verify with *. The current menu emphasizes larger algorithms. Read the input contract before the implementation: verification applies to inputs that satisfy it. Annotated[T, Refine(...)] retains the Python type T; the lambda’s first argument names the refined value and later arguments name the function inputs it depends on.

Keep a value within bounds

clamp(value, lower, upper) accepts an ordered interval: lower <= upper. It returns the nearest value in that interval. The result contract says both that the result lies within the bounds and that it equals min(upper, max(lower, value)).

The second condition matters. Always returning lower would satisfy the range condition, but would change values that already fit. This is the difference between proving an output is permitted and proving it is the intended output. Negative bounds and the single-point interval lower == upper are valid inputs.

Try changing the final return value to return lower. Verification should report unproved; an incomplete proof is not itself a validated execution witness. Independently, clamp(1, 0, 2) then returns 0 instead of 1.

Allocate within capacity

allocate(available, requested) takes two nonnegative quantities and returns (granted, remaining). This operation can represent distributing work, space, or a budget, without needing a specific unit or storage system.

The tuple fields have the refined type Nat, so neither may be negative. The result contract also states:

  • granted == min(available, requested): grant as much as possible.
  • granted + remaining == available: preserve the original quantity.

Nonnegativity alone would admit (0, 0) for every request. Conservation alone would admit granting nothing even when capacity is available. Both the exact allocation rule and conservation belong in the contract. Zero capacity, zero demand and demand greater than capacity are all valid cases.

Subtract one extra unit from the returned remainder to create a deliberate conservation bug with the same contract. Verification should report counterexample. For example, (available, requested) = (3, 1) would produce (1, 1), losing one unit.

Read an exact window

read_window(data, cursor, count) returns (items, next_cursor). The input contract allows 0 <= cursor <= len(data) and 0 <= count <= len(data) - cursor. The result contract requires all of:

  • Exactly count items, with the contents of the requested slice.
  • A cursor advanced by exactly count.
  • A next cursor no greater than the data length.

Python slicing silently returns fewer items when an endpoint is too large. The input contract prevents that behavior here; absence of an IndexError alone would be a weaker guarantee. Reading zero items at the end is allowed.

read_pair makes two one-item reads. Its stronger input contract promises two available items. The first call’s result establishes the second call’s valid cursor, and the one-item length guarantees justify both [0] accesses. The final contract identifies the two returned values in the original data.

Try adding one to the returned cursor in read_window: its exact cursor contract fails. Alternatively, weaken read_pair to require only one available item. The second call can no longer be justified. The cursor edit reports unproved; the weakened input reports error because even the return contract data[cursor + 1] is not defined for every admitted input. With data = [7] and cursor = 0, the latter edit admits an input that reaches an empty second window and fails at [0] during Python execution.

Scope and provenance

The three accepted introductory samples contain four functions, all expected to be verified with separate exact-target termination evidence. They do not model concurrent access, I/O or machine-width overflow. Annotations do not validate incoming data at runtime. Callers outside the checked code must establish the preconditions. Termination evidence does not prove resource availability.

The user-supplied LiquidHaskell.pdf, especially sections 2.2–2.3 on value constraints and dependent contracts and sections 3.1–3.2 on length constraints, provided conceptual background. The Python implementations, scenarios and explanations here were written for refinepy; they are not translations of the book’s code or prose. These samples make no claim that refinepy supports LiquidHaskell’s user-defined algebraic data types or measures.

The menu removes the earlier arithmetic, first-element, loop-counter and composite-syntax demonstrations. Their small regression inputs remain in scripts/fixtures/wasm-samples.cjs; search, list and partition demonstrations remain in the repository. Signed division is in the numerical menu.

The maintained files are examples/practical/bounds.py, allocation.py and window.py. The web build copies bounds.py into the menu; the other two sources remain directly usable as standalone exercises. The Wasm regression suite checks accepted programs and the four edits above. A separate finite Python check covers boundaries and concrete bug witnesses; finite execution is not the universal proof supplied by the verifier.
