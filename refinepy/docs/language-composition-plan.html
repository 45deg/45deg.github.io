Language composition implementation plan

This work addresses the three high-priority gaps identified in the language review. This document tracks acceptance work; it does not expand the supported language by itself. The specification and support matrix describe shipped behavior.

Required outcomes

  1. Compose supported value types: lists of fixed products, optional list elements, products containing lists, and nested supported containers. Preserve element/field refinements, optional definedness, value equality, variance and stable-state assumptions. Exercise coordinate sequences, missing values and a function returning two partition lists.
  2. Compose fresh list construction across source calls. Derive freshness from checked allocation/alias behavior, not value equality or a postcondition. Permit a caller to append to or update a returned fresh list while preserving inputs. Reject borrowed/mixed-branch results, escaping aliases and unsafe iterator writes. Propagate evidence through dependencies and recursion conservatively; an unsuccessful dependency cannot establish ownership.
  3. Compose contracts and logical functions. Admit product construction and supported product operations in predicates. Extend checked reflection to supported products, optionals and mappings, and total multi-statement definitions. Retain independently checked definedness and termination, argument evaluation, dependency validation and bounded expansion. Preconditions must be accounted for explicitly if partial-domain reflection is introduced; they must never become unconditional equations.

Each outcome needs positive, negative and boundary regression coverage, aligned Guide/Reference/specification/support-matrix updates, rebuilt web documentation, and relevant native checks. Runtime differential checks must cover newly modeled Python operations. Solver uncertainty remains a non-success. Browser/Wasm checks are distinct from native or document checks.

Composite-container representation work

The storage layout now uses one outer array per flattened element leaf, preceded by the container length or mapping domain. Product fields and optional tags keep distinct arrays; nested snapshots produce arrays of shapes and arrays of arrays. Zero-width elements retain the outer shape without a values array. Literal construction, reads, list stores, concatenation, slicing, pointwise maps and element bindings use this layout. Internal SMT tests cover products containing optionals and lists, duplicate mapping keys, negative reads, replacement, reversal, field-wise maps and true/false element predicates.

This is internal representation work, not source admission. The scalar-element frontend gate remains in place. Before removing it, align frontend element contracts and enforce ownership for nested mutable aliases. Then validate the original coordinate, missing-value and partition examples through the frontend and Python execution. Low-level SMT tests alone do not establish those outcomes.
