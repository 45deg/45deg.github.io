Python support matrix

The specification v0.4 defines the supported Python 3.12 domain. This matrix specifies admitted and excluded source forms. A supported construct can yield unproved when a property exceeds the finite inference vocabulary.

Status legend

Status Meaning
P Supported within the stated domain and restrictions below
L Limited: only the listed forms are admitted; nearby forms are excluded
D Unsupported or excluded by an explicit baseline restriction

The inventory does not define complete Python coverage. No row means “all legal Python uses are supported.”

Body code and predicates have different rules. Explicitly reflected total definitions over supported value types can be called in either context; see reflection. A direct body call may use a verified contract while the same call is forbidden inside a logical predicate. Qualified static annotation names such as typing.Annotated do not authorize executable attribute lookup. Every P or L entry is also subject to the module-initialization and stable-state assumptions.

The syntax baseline is Python 3.12. The inventories cover all 28 statement constructors and all 27 expression constructors in its AST grammar, with additional tables for subforms, types, and operations. This is an AST inventory, not every concrete grammar production or standard-library API. Python 3.12’s ASDL source provides the inventory cross-check.

The call rules separate written evaluation order from formal binding. An unresolved call is a non-success, never an implicit trusted contract.

Types and annotation forms

A type annotation does not imply a model for every operation or every runtime implementation accepted by ordinary Python typing.

Container element refinements quantify over the valid snapshot domain with a local element binder. Nested logical map bindings do not change that binder’s scope. Composite element contracts preserve lexical scopes at each nested level.

Pattern and auxiliary AST nodes

The unsupported Match row covers MatchValue, MatchSingleton, MatchSequence, MatchMapping, MatchClass, MatchStar, MatchAs, and MatchOr. ExceptHandler belongs to unsupported exception handling; comprehension is supported only within the restricted ListComp form above.

Function arguments, arg, and keyword fields follow the call restrictions. Import alias fields follow static resolution. A constrained scalar TypeVar is limited as specified above; ParamSpec and TypeVarTuple are unsupported. TypeIgnore supplies no suppression. Accepting a parent cannot bypass a rejected child form.

Turning the matrix into conformance tests

For every P or L row, retain an accepted example, the nearest rejected variant and a semantic edge case. For D rows, test deliberate rejection and a non-success overall result.

Each fixture should record a feature identifier, source, target, expected parse/type/lowering outcome, verifier status, obligation kind, and assumptions. Keep unsupported code distinct from safe code that inference cannot prove. Successful parsing is not a positive verifier test.

The conformance requirements define the required checks. The tables do not establish unrestricted Python coverage.

Reflected functions and lemmas

@reflect admits total loop-free definitions over supported value types in contracts, assertions, preconditions, loop invariants and bodies. Definitions have plain supported annotations and no preconditions. Local assignment/rebinding, flat unpacking, assertions, branches, early returns and None fallthrough are supported, with an optional docstring. Products, optionals and supported containers, including mappings, can compose. Fixed signatures and supported immutable literal defaults are supported. Other reflected functions may be called; ordinary source contracts and trusted models do not supply reflection. All argument evaluations remain checked, including unused arguments.

Loops, container writes, erased proof calls, mutual recursion, generics, effects and refined signatures (including nested field/payload/element contracts) are excluded. Raw-body verification must establish safety for every evaluated read, optional projection and divisor before caller proofs use an equation. Depth beyond 32 definitions or expanded serialized terms above 128 KiB, or statement CFG expansion beyond 128 edges, are unsupported. A lemma is an ordinary verified function with a proposition in its return refinement; calls use the normal-return contract. Recursive refined-None lemmas with explicit checked descent support restricted well-founded induction. See inductive lemmas. A restricted integer/lexicographic-measure checker supports direct recursion and explicitly measured loops; see decreasing measures. Direct recursive reflection admits the same plain supported value types for inputs and result with an explicit checked integer or lexicographic measure. Raw-body safety checks admit guarded indexing. Stored definitions retain the 128 KiB bound; recursive bounded-expansion admission preflight has a separate 4 MiB serialized term budget and produces unsupported on excess. Canonical function calls receive local ground equations up to eight layers for scalar-only signatures or three when a signature contains a container; inductive lemma queries use one layer. Scoped applications stay uninterpreted, and oversized default expansion retries one layer before returning unknown on budget exhaustion. Satisfiable queries containing applications are unknown, never source counterexamples. Composite fields retain source-domain guards and extensional snapshot equality. Composite container elements follow the supported value rules; self-call aliases remain unsupported. See recursive reflection and the specification.
