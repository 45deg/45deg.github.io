Playground Guide Reference

Browser playground

The playground builds the existing Rust verifier and the pinned Z3 4.15.4 source into a single WebAssembly module using wasm32-unknown-emscripten. It runs the same parser, package resolver, inference, final obligations and model validation as the native CLI. The browser provides an in-memory filesystem containing playground.py and a generated configuration. Python source is never executed, uploaded or persisted. No verification backend is required.

Display language

The playground header has an EN / JP switch for English and Japanese. It translates controls, example names, editor search controls and result summaries entirely in the frontend. Switching preserves the source, undo history, selector, current run and existing results. The language preference is saved locally when browser storage is available; English is the default. Python samples, raw verifier diagnostics, proof records, stage identifiers and JSON stay in their original form. Guide and Reference content is available in both languages. Their Python code blocks remain identical. Linked technical documents under docs/ remain in English. The three header pages use client-side navigation without reloading the editor. Direct .html URLs, section links and browser Back/Forward are supported; refreshing still resets the source. Documentation load failures are shown explicitly.

Build and run locally

Use the repository’s pinned Rust toolchain, Emscripten (emcc, emcmake), CMake, a host C/C++ compiler with libclang, curl, SHA-256 tooling, Python 3, Node.js 22 or newer, pnpm 11.1.1 and Pandoc. Native Z3 is not required. The build checks the same Z3 source archive checksum as the native build and uses a separate static-library installation under target/wasm.

rustup target add wasm32-unknown-emscripten
sh scripts/build-wasm.sh
sh scripts/serve-wasm.sh

Open http://127.0.0.1:8000. Choose an example and click Load example, edit the source, then click Verify. The local development server sends Cache-Control: no-store for generated assets so later reloads use the rebuilt verifier. If an earlier server’s assets were already cached, use a fresh local port with REFINEPY_WEB_PORT for the first run after this change. The function selector accepts a function name or *, with the same explicit-target semantics as the native CLI. Results retain the exact report classifications, diagnostics, inference evidence and checked scope. Expand Full JSON report for report schema v3 output. The results start with counts of Verified, Needs review and Failed selected functions. Needs review groups unproved, unknown and unsupported; Failed groups counterexample and error, whose individual meanings remain visible on each card. An error does not necessarily indicate a source bug. Report-level diagnostics appear separately and prevent an all-verified summary. Each card gives a short conclusion and a separate termination summary. Expand Verification details for solver costs, checked scope, inferred invariants, source dependencies and Proof evidence, including ownership records. Full JSON report retains the complete report.

Each result also shows whether termination of that function and its checked calls was verified. A verified contract without that evidence applies to normal returns. Proof evidence expands the original termination, induction, reflection and erased-lemma records. Callee evidence alone never establishes termination of the selected caller; failed or uncertain results cannot show a successful termination summary. The numerical example guide describes one basic range contract and five numerical examples: Fibonacci, integer square root, series summation, exact rational rounding and signed division. Container examples remain regression inputs outside the menu. All menu sources are copied verbatim from maintained Python files by build-web.sh; the Wasm suite checks source equality and proof results. Loading a sample replaces the editor contents and clears its undo history. There is no automatic saving.

The Python editor uses CodeMirror 6 with line numbers, syntax highlighting, completion, bracket matching, folding, undo/redo and search. Tab moves focus out of the editor; use Ctrl+] (Cmd+] on macOS) to indent and Ctrl+F (Cmd+F) to search. The editor becomes read-only while verification runs. The layout uses a neutral header, compact toolbar and adjacent source and result panes; narrow screens stack the panes. Header links open the local Guide and Reference in the same tab.

The English sources are web/guide.md and web/reference.md; their complete Japanese counterparts are web/guide.ja.md and web/reference.ja.md. Maintain both languages together, retaining identical code blocks, section IDs and link destinations. The build renders four fragments under content/ with Pandoc and rewrites local Markdown links to HTML. index.html, guide.html and reference.html serve the same app shell, so static servers need no URL rewrite. web/navigation.js fetches and caches successful fragments, ignores stale responses after navigation or language changes, and reports load failures. web/route.js limits client-side navigation to the three top-level pages. The editor stays mounted, including its undo history, results and active worker. Source is still reset on a full reload and never saved to storage.

Technical Markdown files in docs/ retain their standalone English pages using web/docs-template.html. Update the relevant sources alongside behavior changes, as required by AGENTS.md. Run python3 scripts/check-web-docs.py after building to check bilingual code, anchors, reference links and the direct-entry shells. Pandoc’s syntax token spans use the editor palette in web/style.css to highlight documentation code blocks in both light and dark color schemes. The editor page omits backend and verification-boundary explanations; the linked documentation retains the detailed contract.

CodeMirror and its dependencies are locked in web/pnpm-lock.yaml and bundled locally with esbuild. The browser loads no editor code from a CDN. After frontend edits, reuse an existing Wasm build with:

sh scripts/build-web.sh
sh scripts/serve-wasm.sh

build-wasm.sh also runs this frontend build. Generated bundles and dependencies are ignored; only source, package configuration and the lockfile are committed.

The first build compiles Z3 and can take several minutes. Subsequent builds reuse the generated CMake and Cargo outputs. All compiler caches and browser artifacts are ignored under target/. Set REFINEPY_BUILD_JOBS to control CMake parallelism and REFINEPY_WEB_PORT to change the local server port. If EM_CACHE is unset, the script keeps Emscripten’s generated system libraries in target/wasm/emscripten-cache.

Browser execution boundary

Each verification starts a fresh Web Worker and module instance. Z3 uses a single-threaded build with polling timeouts; no SharedArrayBuffer or special cross-origin isolation headers are needed. The browser must support WebAssembly exception handling, matching the pinned Rust target and the Z3 C++ build. Rust monotonic deadlines and native query timeouts still apply. Cancel terminates the worker, and an independent 90-second browser deadline covers module loading and all selected targets. Cancellation, loading failure and that outer deadline produce no proof result.

The browser solver runs in the same module instead of a child process. It checks the loaded Z3 version, request size, satisfiable models and the target deadline before accepting a result. The native CLI retains its isolated worker protocol. The documented proof assumptions remain applicable to this execution boundary.

The editor accepts one UTF-8 module, at most 1 MiB. Calls within that module work; additional project files, external model manifests, native cache reuse and cancel-file control are not exposed by this UI. Missing source dependencies fail through the ordinary resolver and must not be treated as verified. The full Python support matrix and verification contract still apply. Verification remains conditional. A verified status alone does not prove termination; explicit integer or lexicographic measures can add evidence for direct recursion and measured loops as described in the specification.

Checks

Check result interpretation without a browser or solver:

pnpm --dir web test

After building, run the Wasm integration checks in Node:

node scripts/test-wasm.cjs

They execute the actual generated module against supported contracts, source calls, loop inference, containers, counterexamples and failure boundaries. This is separate from browser UI verification and from the native checks in scripts/test.sh.
